# ruyi

 **`ruyi`** 是一个使用 C 语言实现的轻量级、高性能异步 I/O 库。她聚焦于网络事件与定时事件，在追求极致低延迟的同时，保持高吞吐量

 **`ruyi`** 的开发基于现代硬件与操作系统，其内部实现采用大量新特性（原子操作，POSIX新标准的接口等），其内存分配策略也非常激进，程序启动初期就内存占用就接近100MB， **`ruyi`** 不像其它开发较早的网络库对老旧接口和硬件提供兼容，她期望运行在较新的平台获取到性能支持

## 设计目标

- **极致低延迟**：无锁队列、零拷贝读取、批量写入
- **高吞吐**：单线程 Reactor 跑满网卡带宽，读写低延迟，没有多线程锁争用与缓存失效
- **低抖动**：预分配大内存、标记删除定时器，消除运行时动态分配带来的延迟抖动
- **精简依赖**：仅依赖 C11 标准库与 POSIX 接口，无第三方依赖

## 核心特性

| 特性 | 实现方式 |
|------|---------|
| 单线程 Reactor | epoll (Linux) / kqueue (BSD) |
| 无锁队列 | SPSC / MPSC，基于 C11 原子操作 |
| 零拷贝读取 | 环形数组 + 引用计数，避免协议包投递时的数据拷贝 |
| 批量写入 | `writev` 合并多缓冲区，降低系统调用频率 |
| 高精度定时器 | 最小堆，1ms 分辨率，预分配 $2^{20}$ 槽位 |
| 异步 DNS | 独立线程池，解析结果通过 SPSC 队列回调至 Reactor |
| 零开销日志 | 网络线程仅做无锁入队，格式化与时间戳转移至日志线程 |

## 模块详解

### Network

采用**单线程 Reactor**模型。网卡吞吐量和TCP协议栈处理速度依然是现代网络数据处理瓶颈，单线程足以吃满网络带宽，同时避免了多线程带来的缓存失效与锁争用，这是实现极致低延迟读写的最优选择

#### write
业务线程投递写请求后，Network 线程全程接管：
- 数据挂入**待写链表**
- 发送时通过 **`writev`** 将多个小缓冲区打包为单次系统调用
- 若 TCP 发送缓冲区满，则注册 `EPOLLOUT`，等待可写事件继续发送

> 现代 TCP 协议栈的发送缓冲区会动态伸缩，`writev` 对小包场景的吞吐提升非常明显

#### read
接收端是 **`ruyi`** 设计最重，也是前前后后推倒方案最多、耗时最久的部分； **`ruyi`** 自身实现了`pack_len + payload`，读策略的目标只有一个：**read之后的数据零拷贝，直接向上层投递完整数据包**

- **环形数组**：每个连接默认8个槽位，每个槽位携带 **384KB** 大缓冲区 + 引用计数。
- **引用计数投递**：每读到一个完整数据包，引用计数 `+1`，以**引用形式**向上层投递；上层处理完毕后计数 `-1`，槽位自动回收
- **放弃 `readv`**：最初设计使用 `readv` 拼接多缓冲区，但 64KB 大包跨缓冲区 `memcpy` 耗时达微秒级，反而劣于一次空系统调用（~100ns）。最终采用单缓冲区直接 `read`，在 384KB 槽位下效率更优
	+ 这里有一个取舍，`readv`的做法更适用于高频小数据包，但考虑到实际情况，默认 384KB 的缓冲区已经足够大，如果高频小数据使得每次`read`都读满，那么多几次系统调用对于拷贝 384KB 的数据来说开销可以忽略不计

#### 连接生命周期
- 支持配置空闲超时（默认 5 分钟），超时连接会被 GC
- 默认连接数65536，主循环一次只对一个槽位进行 GC ，超时检测存在理论最大 **~13s** 的粒度延迟，**不适合做精确心跳**。如果需要精确心跳需要用户在应用层自行实现

### Timer

定时器也是最耗费心神的设计之一，单是对于存储的数据结构就经历多轮抉择：

+ `时间轮` 排除时间轮的原因有两点：
	+ **精度受限** 即便是软实时系统，在当今的硬件加持下，如果系统流水任务不繁忙，调度延迟已经可以到达毫秒级，这也是 **`ruyi`** 提供1ms间隔分辨率的原因
	+ **重分配** 低级轮跑完一轮后，从高级轮重新分配，在任务繁重的情况下会带来抖动，这与 **`ruyi`** 的设计理念不符
+ `跳表` 跳表拥有 $O(1)$ 的弹出最先到期事件的时间复杂度，理论上是最适合的数据结构。在这里也纠结了挺长一段时间，但是在浏览过一些数据结构性能对比的博客之后还是舍弃，毕竟最小堆所带来的缓存局部性优势太明显
+ `树` 不考虑内存使用的情况下，选择树还不如选择跳表，毕竟树获取最值元素也需要 $O(log N)$ 的时间复杂度

最终采用 **最小堆** ：
- 预分配 $2^{20}$ 个槽位，约一百多万个定时事件位置，后续直接按2的倍数增长
- 提供 **1ms** 时间分辨率
- 删除采用**标记-延迟删除**：通过**开放地址法哈希表**存储待删 ID，避免链地址法的指针跳转与额外数据结构依赖
	> 选择何种数据结构存储待删 ID 也耗费了不少时间，流行的选择无非就是树或者哈希表，考虑到删除操作相比于插入操作来说可能少之又少，哈希表应该更好。但是要使得哈希表性能更好，又得引入冲突时使用的数据结构如链表，树等， **ruyi** 的设计希望是精简的，所以在其内部并不想实现过多的数据结构。后来又考虑了位图等实现，但无论如何优化都处理不了 ID 自增长的情况。苦闷之下突然意识到，以前所实现的[哈希表](https://github.com/olberix/structdata#9)使用的是链地址法，如果使用开放地址法，对于自增长id，面对固定的模数（数组长度），开放地址法的方案简直完美

### Logger

日志模块的设计目标是：**网络线程的零开销**

- **SPSC 无锁队列**：网络线程仅做无锁入队，不执行任何格式化
	> 日志模块并不需要很好的输出性能，只需要提供极高的输入性能给网络线程使用，将其阻塞时间降至最低。原本采用的是无锁环形数组，在 **ruyi** 内部实现各种无锁队列之后改用 **SPSC 无锁队列** ，彻底杜绝丢失日志的可能
- **时间戳转移**：时间获取与字符串格式化全部放在日志线程执行。虽然现代 Unix 时间函数已无需进入内核态，但频繁格式化仍是不可忽视的 CPU 开销；对于网络日志，保证时序的正确性便可，牺牲一点时间精度能更大限度压榨网络事件的性能

### DNS

为避免解析阻塞 Reactor 主循环， **ruyi** 将 DNS 解析拆分为独立线程：
- `ruyi_net_listen()` / `ruyi_net_connect()` 内部自动进入 DNS 队列
- 解析完成后通过 SPSC 队列回调至 Network 线程，继续后续 I/O
- 上层应用如果不是 HTTP 类连接场景下，DNS 线程大部分时间处于睡眠状态，不消耗 CPU

## 构建与平台要求

### 环境

+ OS: linux、BSD、macOS
+ Compiler: GCC >= 9 或 Clang >= 10（需完整 C11 的支持）
+ Arch: x86_64 或 aarch64（64位系统，提供完成的内存序与原子指令性能）

### 编译

```shell
git clone https://github.com/olberix/ruyi.git
cd ruyi
./build.sh
```
