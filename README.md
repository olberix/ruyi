# ruyi

 **`ruyi`** 是一个使用 C 语言实现的轻量级、高性能异步 I/O 库。她聚焦于网络事件与定时事件，在追求极致低延迟的同时，保持高吞吐量

 **`ruyi`** 专为现代硬件与操作系统设计，其内部实现基于大量新特性（原子操作，POSIX标准的新接口等），同时大量采用空间换时间的激进策略（预分配内存）， **`ruyi`** 不对老旧接口提供兼容，避免其运行在不能发挥出相应性能的老旧平台

## 核心特性

+ 单线程 Reactor 模型：目前，网卡吞吐量和TCP协议栈处理速度依然是网络处理瓶颈，单线程 Reactor 模型足以跑满带宽，这是实现极致低延迟读写的最优选择
+ 高性能定时器：基于最小堆实现，提供 1ms 的高精度定时，并通过预分配内存等方式减少运行时抖动
+ 无锁交互：异步队列全都采用SPSC、MPSC等无锁队列，交互延迟达到最优
+ 零拷贝读取策略：为每个连接槽位预置大缓冲区，并通过 环形数组 + 引用计数机制管理内存，实现数据读取后的零拷贝提交。缓冲区用完后不释放，存储在内部供下一次使用
+ 批量写入优化：使用 writev 系统调用合并多个待发缓冲区，有效降低小数据包高频发送时的系统调用开销
+ 异步 DNS 解析：DNS 解析任务独立线程池处理，不会阻塞主事件循环

## 模块详解

### Network

采用**单线程 Reactor**模型。在网卡吞吐成为瓶颈之前，单线程足以吃满网络带宽，同时避免了多线程带来的缓存失效与锁争用

#### write
业务线程投递写请求后，Network 线程全程接管：
- 数据挂入**待写链表**
- 发送时通过 **`writev`** 将多个小缓冲区打包为单次系统调用
- 若 TCP 发送缓冲区满，则注册 `EPOLLOUT`，等待可写事件继续发送

> 现代 TCP 协议栈的发送缓冲区会动态扩缩，`writev` 对小包场景的吞吐提升非常明显

#### read
接收端是 **`ruyi`** 设计最重，也是前前后后推倒方案最多、耗时最久的部分，其目标只有一个：**消除一切不必要的数据拷贝**

- **环形数组**：每个连接默认8个槽位，每个槽位携带 **384KB** 大缓冲区 + 引用计数。
- **引用计数投递**：每读到一个完整协议包，引用计数 `+1`，以**引用形式**向上层投递；上层处理完毕后计数 `-1`，槽位自动回收
- **放弃 `readv`**：早期设计使用 `readv` 拼接多缓冲区，但 64KB 大包跨缓冲区 `memcpy` 耗时达微秒级，反而劣于一次空系统调用（~100ns）。最终采用单缓冲区直接 `read`，在 384KB 槽位下效率更优

#### 连接生命周期
- 支持配置空闲超时（默认 5 分钟），超时连接会被 GC
- 默认连接数65536，主循环一次只对一个槽位进行 GC ，超时检测存在理论最大 **~13s** 的粒度延迟，**不适合做精确心跳**。如果需要精确心跳需要用户在应用层自行实现

### Timer

定时器也是最耗费心神的设计之一，单是对于存储的数据结构就经历多轮抉择：

+ `时间轮` 排除时间轮的原因有两点：
	+ **精度受限** 即便是软实时系统，在当今的硬件加持下，如果系统流水任务不繁忙，调度延迟已经可以到达毫秒级，这也是 **`ruyi`** 提供1ms间隔分辨率的原因
	+ **重分配** 低级轮跑完一轮后，从高级轮重新分配，在任务繁重的情况下会带来抖动，这与 **`ruyi`** 的设计理念不符
+ `跳表` 跳表拥有 $O(1)$ 的弹出最先到期事件的时间复杂度，理论上是最适合的数据结构。在这里也纠结了挺长一段时间，但是在浏览过一些数据结构性能对比的博客之后还是舍弃，毕竟最小堆所带来的缓冲局部性优势太明显
+ `树` 不考虑内存使用的情况下，选择树还不如选择跳表，毕竟树获取最值元素也需要 $O(log N)$ 的时间复杂度

最终采用 **最小堆** ：
- 预分配 $2^{20}$ 个槽位，约一百多万个定时事件位置，后续直接按2的倍数增长
- 提供 **1ms** 时间分辨率
- 删除采用**标记-延迟删除**：通过**开放地址法哈希表**存储待删 ID，避免链地址法的指针跳转与额外数据结构依赖
	> 选择何种数据结构存储待删 ID 也耗费了不少时间，流行的选择无非就是树或者哈希表，考虑到删除操作相比于插入操作来说可能少之又少，哈希表应该更好。但是要使得哈希表性能更好，又得引入冲突时使用的数据结构如链表，树等， **ruyi** 的设计希望是精简的，所以在其内部并不想实现过多的数据结构。后来又考虑了位图等实现，但无论如何优化都处理不了 ID 自增长的情况。苦闷之下突然意识到，以前所实现的[哈希表](https://github.com/olberix/structdata#9)使用的是链地址法，如果使用开放地址法，对于自增长id，面对固定的模数（数组长度），开放地址法简直完美适用于这种情况

### Logger

日志模块的设计目标是：**网络线程的零开销**

- **SPSC 无锁队列**：网络线程仅做无锁入队，不执行任何格式化
	> 日志模块并不需要很好的输出性能，只需要提供极高的输入性能给网络线程使用，将其阻塞时间降至最低。原本采用的是无锁环形数组，在 **ruyi** 内部实现各种无锁队列之后改用 **SPSC 无锁队列** ，彻底杜绝丢失日志的可能
- **时间戳转移**：时间获取与字符串格式化全部放在日志线程执行。虽然现代 Unix 时间函数已无需进入内核态，但频繁格式化仍是不可忽视的 CPU 开销；对于网络日志，保证时序的正确性便可，牺牲一点时间精度能更大限度压榨网络事件的性能

### DNS

为避免解析阻塞 Reactor 主循环， **ruyi** 将 DNS 解析拆分为独立线程：
- `ruyi_net_listen()` / `ruyi_net_connect()` 内部自动进入 DNS 队列
- 解析完成后通过 SPSC 队列回调至 Network 线程，继续后续 I/O
- 上层应用如果不是 HTTP 类连接场景下，DNS 线程大部分时间处于睡眠状态，不消耗 CPU

## 构建与平台要求

### 环境

+ OS: linux、BSD、macOS
+ Compiler: GCC >= 9 或 Clang >= 10（需完整 C11 的支持）
+ Arch: x86_64 或 aarch64（64位系统，提供完成的内存序与原子指令性能）

### 编译

```shell
git clone https://github.com/olberix/ruyi.git
cd ruyi
./build.sh
```
